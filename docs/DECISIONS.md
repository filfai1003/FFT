# Decisions log

Choices made while turning the design into code, mostly where the design or `PROJECT.md` was
ambiguous or inconsistent. The owner delegated these decisions on 2026-10-08. Revisit any of them
before the phase that depends on it.

## Stack and tooling

| Decision | Why |
|---|---|
| Flutter template removed; Expo SDK 57 at the repo root, routes in `src/app` | The Expo template uses `src/app`; alias `@/*` → `src/*`. |
| Zustand for UI/appearance/toast state, TanStack Query for server state | Small, no boilerplate. The active workout session will NOT depend on the Query cache. |
| `i18next` + `expo-localization`, typed keys; ESLint rule `react/jsx-no-literals` forbids literal JSX text | Enforces "no hardcoded strings". Props such as `accessibilityLabel` are not caught by the rule: review by hand. |
| Sheet and Toast written in-house (RN `Modal` / `Animated`) | No heavy dependency; behaviour is simple and fully testable. |
| Supabase CLI as a devDependency (`npx supabase`) | No global install. |
| DB checks run twice: on embedded Postgres in `npm run check` (`db:verify`, fast, no Docker) and as pgTAP on the real stack (`npm run db:test`) | A quick check must not need Docker; the real stack confirms it. |
| Auth session in AsyncStorage for now | Phase 1 decides whether to encrypt it (health data). |
| Open Food Facts rows are written by an Edge Function with the service role (Phase 3); users cannot write global rows | Keeps RLS strict ("everyone writes only their own rows"). |

## Resolved design inconsistencies

1. **Muscles**: the Create exercise chips (chest, back, shoulders, biceps, triceps, legs, glutes, abs) are stored as is; strength groups (Chest, Back, Shoulders, Legs, Arms, Core) are derived: biceps/triceps → arms, abs → core, glutes → legs (`public.strength_group`).
2. **Shared screens** (Exercise detail, Plan detail, Session detail) become root-level routes (`src/app/exercise/[id]`, …) so they can be opened from the session, Today and Progress. The tab bar is shown on them only when entered from a tab.
3. **Back/Minimize** return to wherever the screen was opened from (native stack), not to the fixed target drawn in the mockups.
4. **Resume banner**: a "Session in progress" row is added to Today and Train (not drawn: mockup to be shown before building it).
5. **Fixed-meals mode**: "Log the foods instead" returns to the fixed-meals log (not to the count-foods one). Today's "Meal" shortcut becomes "Mark next meal done" in that mode.
6. **Recipes** is part of the food-search modal flow (no tab bar), not a tab push.
7. **Exercise picker** takes a `returnTo` param so it also serves Empty workout and adding an exercise during a session.
8. **Session actions** not drawn (remove/replace/add exercise, per-set rest): a "⋯" menu next to "Exercise details".
9. **Non-`weight_reps` exercises** (reps, time, distance/time) get row variants in the session screen (Phase 2).
10. **Reorder** ("HOLD TO REORDER") also gets move up/down buttons for accessibility and one-hand mode.
11. **Controls without a screen** (New plan, plan "⋯" menu, notifications bell, calendar, water/weight quick log sheets, See plans, Help & feedback) are designed when their phase arrives and shown before building.
12. **Plan status**: `workout_plans.status` (`draft | active | archived`) replaces the boolean `active`; one active plan per user.
13. **DB additions**: `session_exercises` (order/rest/notes of each exercise in a session), `body_goals` (weight target), `nutrition_goals.water_ml` and `maintenance_kcal` (enables the 25 % deficit rule in SQL), `user_settings.water_glass_ml`, `consents.policy_version`, `workout_sessions.day_name` (snapshot), `foods` source/owner constraint.
14. **Strength score** only includes exercises trained on at least two different days in the period (one day has no "change").
15. **Day / time zone**: `exercise_e1rm_daily` groups by the session start in the profile time zone.
16. **Activity levels** follow the Personal info screen (Mostly sitting / Light / On my feet / Physical job → 1.2 / 1.375 / 1.55 / 1.725).
17. **Suggested target**: maintenance −10 % (lose fat), 0 (maintain), +10 % (build muscle), rounded to 50 kcal and never below the safety floor. This reproduces the mockup (2600 → 2350).
18. **Sex** for the formula is `male | female` only. **Age**: onboarding will block under-18s (decided in Phase 1, not in the DB).
19. **Theme**: dark only for now; the Light/System options stay disabled until the light theme is designed.
20. **Accent colours**: the 6 options of `tokens.json`; text on the accent picks black or light for ≥ 4.5:1 contrast (the white accent needs black text).

## Decided while building Phases 1–5

21. **Auth session** is stored encrypted (AES key in SecureStore, ciphertext in AsyncStorage). Apple / Google sign-in is deferred: email + password only for now.
22. **Shared screens** (exercise detail, session detail) are re-exported inside each tab's folder instead of being root routes, so the tab bar and back stack stay correct.
23. **Notifications**: `src/lib/notifications.ts` is a web no-op, `notifications.native.ts` is the real local-notification code (expo-notifications has no web build).
24. **Edge Functions** (`off`, `delete-account`) need `supabase functions serve` locally (`supabase start -x imgproxy,edge-runtime`).
25. **Demo data**: `supabase/scripts/demo-data.sql` fills 12 weeks of body entries and workouts for the first onboarded user (local only).
26. **Photos**: private bucket + signed URLs; blur-until-tapped and device lock are client settings in `privacy-store`.
27. **Withdrawing health consent** pauses the app behind `ConsentGate` (give consent again, export or delete).
28. **Fixed-meals auto-split** (only the Auto-split button; every value stays editable): same base calories per meal, a main meal gets 1.4x, the meal right before the workout shifts 12% of its calories from fat to carbs, the one right after shifts 8% from fat to protein; the other meals absorb the difference so the day keeps its macro totals. Stored as `fixed_meals.is_main` and `fixed_meal_plans.workout_after_meal_id`.
29. **Recipes removed** from the product (screens, routes, tables `recipes`/`recipe_items`, view `recipe_nutrition`, `food_logs.recipe_id/servings`): migration `20261009100000_remove_recipes.sql`.
30. **Meals stay on target**: editing a meal in the fixed-meals plan re-shares the rest between the other meals (`rebalanceMeals`); one meal can never take more than the whole day. Auto-split works from the macro targets (calories = 4/4/9 of those macros).
31. **Onboarding** lets you set the macro split (independent percentages) and set up your meals, main meals and workout position with the same editor as the plan (`MealPlanEditor`).
32. **First workout plan** becomes active right away; a workout with nothing logged is replaced (with UNDO) when you start another one.
33. **Offline mode** ("Use without an account" on the sign-in and setup screens): no account, no sync; everything is saved on the device. `getSupabase()` returns a local client (`src/lib/local-db`) with the same API as supabase-js (query builder, nested selects, the 3 views, `last_sets`, storage, `delete-account`), backed by an in-memory copy of the tables saved to IndexedDB (web) or files (iOS/Android). Same schema rules as the SQL (checks, unique indexes). Leaving offline mode keeps the data for next time; Delete account wipes it. Open Food Facts search is online-only. No migration between modes.
34. **Free accounts keep no data online**: the server only stores the account (email + password; the empty profile row created at sign-up). All user data — plans, workouts, food, body, photos, settings, consents — is saved in the on-device database (`src/lib/local-db`), one database per account id, so accounts on one device never mix. `getSupabase()` = data (local unless `isPremium()`), `getAuthClient()` = server (auth, Edge Functions). Premium accounts keep their data online instead (see 38). Open Food Facts (free, open product database) is searched through the `off` function with an account; without one, or when our server cannot be reached, the device asks Open Food Facts directly (only the barcode or the search words are sent). Found products are copied to the device, one per barcode. Delete account removes the server account and this device's data. Logging in on another device finds no data (no sync, no backup).

35. **AI plans & import** (Profile → AI plans & import): one JSON exchange format (`domain/plan-import.ts`: `workout_plan` and/or `diet_plan`). Manual mode copies a prompt (goal and body basics, never the name; the format; the exercise list) for any AI chat and imports the pasted answer after a preview. The chat uses the user's own API key (Anthropic, or any OpenAI-compatible server), called straight from the device; the key is stored with the auth-session storage (encrypted on phones). The AI sees the current plans and diet and returns whole plans; the user reviews them before anything is saved. Changing an existing plan (same id) archives a copy first ("… (before AI)"). Safety rules still apply to imported diets (≥ 1500 kcal, ≤ 25% deficit); meals are rescaled to the daily target. Exercises not in the library are created only when the AI gives muscle and equipment, otherwise skipped.
36. **AI assistant with tools** (Profile → AI plans & import → chat; needs the user's own API key). The chat is an agent loop (`src/features/ai/agent/`): the model can call tools, the app runs them and gives back the results until the model answers in text (max 10 steps). Works with Anthropic (tool use) and any OpenAI-compatible server (function calling). Reading tools (`get_overview`, `get_day`, `get_history`, `get_body`, `get_workouts`, `get_workout_plans`, `get_diet`, `search_foods`, `list_exercises`) run at once; every changing tool (`log_body`, `create_food`, `update_food`, `delete_food`, `log_food`, `remove_food_log`, `log_water`, `set_meal_status`, `set_nutrition_goal`, `propose_plans`) first shows what it will do and runs only after Approve; most can then be undone (card button and 5 s toast). Tools reuse the app's own mutations, so the rules stay the same (calorie floor and deficit limit, macros must add up, logged values copied). Conversations (several) are saved on the device, per account, and removed with the account. Manual mode (no key) stays one question and one answer: the prompt carries a snapshot of the user's data (today, last 14 days, weight, workouts, plans, diet, own foods) and the answer may contain `actions` (the same changing tools, except plans which have their own keys) that are previewed and applied with one button. The data an assistant reads goes to the provider with the user's key; the name is never sent.
37. **Redesign (2026-10)** after the "FFT redesign" canvas: light-first look (warm off-white, white cards, Figtree, sentence case, fills for progress) replacing the dark dot-matrix style; dark stays available. Two settings: app theme and workout theme (light / dark / phone), both light by default; stored in user_settings (`theme`, `workout_theme`; rows saved before this start on light). Navigation: four tabs (Home, Diet, Train, Progress) and a central "+" that opens the Add sheet (food, scan, water, weight and body, workout, photo, recent foods, coach); Profile opens from the avatar on Home, the coach from the button next to it. Home keeps the customisable widgets (calories with a 270° arc and macro bars first, workout, water as a filling glass, a new weight widget, creatine, calendar); the AI bar is off by default. The workout screen has one big "Done set N" button between previous/next, and the rest timer is a ring. The animated/dot-grid backgrounds and the dot-matrix setting are gone.
38. **Premium = data online + the web app.** Premium today means VIP (set from the admin panel); paid plans come later and will only change `is_premium()` on the server. Free accounts still keep everything on the phone and the server refuses their data (restrictive row level security: inserts and updates need `is_premium()`; reading and deleting stay allowed so data can be taken back). At every start the app asks the server (`src/features/premium/use-plan-gate.ts`): when premium starts, the phone's rows and photos are uploaded (same ids; photos moved to `<user id>/`), then the phone copy is erased; when premium ends, everything is downloaded to the phone, then the server copy is erased (`clear_my_online_data()` and the photo files). If a move fails nothing is lost and it is retried at the next start (going up, the user can keep working on the phone meanwhile). A second phone that goes online keeps the plan, meal plan and workout already active online (its own become inactive). (Superseded by 40: premium devices also work on their own database and sync in the background.) The web app (`web/`, https://web-fft.up.railway.app) needs an account: premium accounts get the full app on their online data; other accounts only see the Premium page (and can sign out); there is no account-less mode on the web. Catalogue exercises have the same ids on the server and on the phone (derived from the slug; `seed.sql` is applied by the server at every start).
39. **Exercise images**: every catalogue exercise has a 512×512 picture in one style (faceless grey mannequin, chrome highlights on the working muscles, dark equipment, black background), made with Meshy image-to-image from the original bench press and deadlift pictures (`tools/exercise-images/`: `prompts.json` per exercise, `generate.mjs`, `compress.mjs` saves them as greyscale PNGs, about 75 KB each). `default.png` is shown for exercises without a picture (the user's own ones). Images ship with the app; `npm run db:seed` lists them in the catalogue.
40. **Premium sync: local first, last change wins.** Every device (phone or web) reads and writes its own database, so actions are instant and work offline. For premium accounts each written row goes to an outbox (one entry per row, its latest state and the time of the action); in the background (right away, 1.5 s after a change, every 30 s, when the app comes back) the outbox is sent (`sync_push`) and the server's changes since the last visit come back (`sync_pull`, cursor = the server's own clock, 2 min overlap). Conflicts: per row the most recent action wins, wherever and whenever it arrives (the server keeps the client's `updated_at`; older changes arriving later are ignored); the same change sent twice changes nothing; a deletion wins over changes made before it and leaves a tombstone so other devices delete too (cascades included). Rows the server refuses for good (a rule) are dropped from the outbox instead of blocking the others; network errors keep everything for the next try. Photos are uploaded with their row and downloaded when missing. When premium starts the device's rows are all queued (nothing is erased); when it ends one last full pull keeps everything on the device, then the server copy is cleared. The premium status known on the device is used at start (no waiting); the server is asked in the background. Limits: the clocks of the devices are trusted; a row is the unit (two fields of the same row changed on two devices: the later row wins whole).
41. **Generic foods** (apple, rice, chicken breast…): about 3000 foods per 100 g from the CIQUAL table (ANSES, Etalab Open Licence 2.0, credited as "Ciqual (ANSES)" on each food), English names only like the rest of the app. Imported with `supabase/scripts/import-ciqual.js` into `supabase/data/generic-foods.json`; `npm run db:seed` puts them in `seed.sql` (server, same ids `cf000000-…-<code>`) and in the app (`local-db/generic-food-table.ts`, read straight from there and never stored in each user's database). Search shows your own foods first, then the closest names ("apple" → "Apple, …" before "Apple juice" before "Pineapple"). Packaged products still come from Open Food Facts (barcode and search). The USDA table was considered as a second source but CIQUAL alone covers the common foods; it can be added the same way.
42. **Plans: free, supporter, premium.** Free = everything on the phone. Supporter (2 €/month) = + data synced online and the web app (API and MCP access next). Premium (20 €/month) = + the AI coach inside the app with no API key: requests go through our server (`ai` function), which calls OpenRouter with the server's key (`OPENROUTER_API_KEY` on the `api` service, model `AI_MODEL`, default `anthropic/claude-haiku-4.5`; the AI tab of the admin panel overrides it with no redeploy, table `app_settings`) and takes the real cost (OpenRouter reports it in USD; `EUR_PER_USD`, default 0.92) from the account's AI credit: 10 € a month (half the price), what is not used carries over up to 15 € (150 %), topped up lazily on the first use of each month (`ai_refresh_credit`). An answer is capped at 2048 tokens; with no credit left the coach says so (own key still possible). Plans are set in the admin panel (sudo; VIP accounts became premium); payments later. `my_plan()` gives the app the plan; `is_premium()` (row level security) now means "can keep data online" (supporter or premium). Credit tables: `ai_credit`, `ai_usage` (readable by their owner, written only by the server).

43. **Import, API and MCP.** Privacy & data can import an earlier export (ZIP): nothing on the device is deleted, a row is added or replaces the one here only when it was changed later (like the sync), rows and photos become this account's, and an imported active plan / fixed-meal plan / workout yields to the one already active. Supporter and Premium get a personal API: personal tokens (made on the server, shown once, only the SHA-256 kept, revocable with UNDO, at most 10) on the page Settings → API & MCP; the api service answers REST at /v1 and MCP at /mcp (stateless Streamable HTTP) on its own public domain fft-api (Kong would need the anon key), running each request as the token's user so row level security applies; 120 requests a minute. Tools: profile, day summary, food log (read, add by food id or by values, delete), food search, water, body measurements (one entry a day), workouts, goals. Details: docs/API.md.

44. **Sign in with FFT for AI apps.** Claude and ChatGPT add remote MCP servers only through OAuth (no fixed token header), so the api service is also an OAuth 2.1 server: discovery (.well-known), dynamic client registration, a sign-in page of its own (FFT email + password, checked by the auth service; free accounts are refused), PKCE S256, access tokens of 7 days with refresh. A connection is an api_tokens row (named after the app, revocable in the app); signing in again from the same app replaces the old connection. In the app the buttons Add to Claude / Add to ChatGPT copy the address and open the connectors page (neither app has an install link, so pasting stays one step). Personal tokens remain for other tools (Claude Code, scripts).

45. **Passwords without an email service.** Sign in stays email + password (Sign in with Google was tried and taken back: it needs a Google Cloud project and consent screen). Profile → Password changes it (current password checked by signing in again, then `updateUser`; hidden in account-less mode). Forgot password? on the sign-in screen sends a request (`request_password_reset`, callable without an account, same answer whether the email exists, at most 3 a day per email and 100 an hour in all) to the admin panel tab Password resets (badge with the open count); the admin, in sudo mode, sets a temporary password (shown once, never stored, logged as `password.temporary`), emails it by hand with the prepared mailto, and the user replaces it in Profile → Password. Requests are kept 7 days after being handled in the list.

46. **Automatic error reporting, on our own server.** No external service (Sentry was the alternative): the app sends crashes (global handler, and on the web window errors and unhandled rejections), screens that fail while drawing (root ErrorBoundary, with Retry), failed queries and mutations (TanStack Query caches, with the query key) and sync failures (with the table) to `report_error`, callable with or without an account. Only the error goes: message, stack, kind, small context, platform, app version and update id; never user data. Not sent: development builds, network failures (the app works offline by design), the same error twice within a minute. Limits: 30 an hour per account, 300 for all account-less phones, 3000 in all; kept 60 days. The admin panel tab Errors groups them by fingerprint (message and first stack lines with numbers and ids blanked), shows times, accounts, platforms and versions, the latest stack, and Fixed (sudo) deletes a problem's reports so a return shows up as new.

47. **No more Supporter: every account is online.** Instead of a weekly backup for free accounts, the Supporter plan (2 €) is removed and what it gave goes to everyone: data synced online (every device, web app, nothing lost when changing phone), API and MCP (tokens and Add to Claude / ChatGPT). Premium (20 €) keeps only the AI coach included in the app with its monthly credit. Supporter rows became free (`user_plans` now only holds premium); `is_premium()` (the name the row level security rules use) now means any signed-in account; the token and OAuth checks no longer look at the plan. On the device the plan gate treats every account as online, so a free account that kept its data on the phone queues it all for upload at the next start (nothing is erased, DECISIONS 40). The account-less mode stays on the phone only.

48. **Next weight suggestion** (version A of the mock-up: already filled in). When a workout starts, each weighted exercise with target reps looks at its last session (`domain/progression.ts`): every working set at the top of the range ("6-8" -> 8) = one step up (2.5 kg / 5 lb; dumbbells 2 kg / 5 lb, rounded to a loadable weight); every working set below the bottom = about 5% down (at least one step); otherwise the same weight and one more rep. Working sets = the heaviest weight of last time (lighter warm-ups are left alone). The sets start at the suggested weight and a card above them says why, with Keep <last weight> (and back). No suggestion for bodyweight and bands, without target reps (exercises added on the go) or without history. Units → I have small plates halves the barbell and machine step (1.25 kg / 2.5 lb; `user_settings.small_plates`); kg are shown with up to 2 decimals so 81.25 stays 81.25.

49. **Same as yesterday** (count-foods diary): an empty meal whose meal the day before has entries shows one row, Same as yesterday, with the foods and the calories; one tap copies them into the shown day as new entries (values as logged, like every log), with UNDO in the toast. Only the day before and only while the meal is empty, so the row never gets in the way.

50. **How to perform.** Every catalogue exercise has three or four short steps and one or two common mistakes (`src/features/train/how-to.json`, by slug; catalogue data in English like the exercise names, so not in i18n), shown first in the exercise page (also reached from the workout with the info button). A test checks that every catalogue exercise has one. The user's own exercises have none.

51. **Android home screen widgets** (react-native-android-widget; a new APK). Five widgets: Calories (arc with kcal left, P/C/F bars; opens Diet), Next workout (the up-next plan day with Start, or trained today; opens Train), Water (glasses of the day and + one glass: the link fft://add-water?from=widget adds it and shows Home with UNDO (without the parameter the page only goes Home)), Weight (latest and 7-day change; opens Body), Supplements (taken today). They follow the app's look in the phone's light or dark theme, with Figtree. Data: the app writes a small snapshot (AsyncStorage) whenever what they show changes (WidgetBridge, mounted on Android when signed in) and redraws them; the widgets never open the database. Every 30 minutes Android redraws them from the snapshot, and a snapshot of an earlier day shows that day's totals as zero, so the new day starts right even with the app closed. Signing out clears them. Taps open the app (deep links); nothing is changed from the widget itself, except water through the app. The widget task is registered in `index.js` (the new entry, which loads Expo Router). The widget views file starts with 'use no memo': the library calls the components as plain functions, and the React Compiler's memo hooks in them failed outside React, leaving every widget empty (transparent). A widget that still cannot be drawn shows a plain FFT card and the error goes to the admin panel (kind widget); a test builds every widget with the library's own tree builder.

52. **Rest timer in the notification** (Android). During the rest an ongoing, silent notification shows the countdown, drawn by Android itself (a chronometer counting down to the end), so it keeps going on the lock screen and with the app asleep; it disappears at the end by itself (and when the rest is skipped or the workout ends). The alert with sound at the end stays the expo-notifications one. `expo-notifications` has no countdown, so it is a small local module (`modules/rest-timer`, Kotlin, NotificationCompat); elsewhere it does nothing. Both follow the Rest timer notification setting.

53. **Supersets.** In the day editor an exercise can be linked with the next one (Superset with the next exercise); consecutive links make one superset (A1 + A2, or three in a row), labelled A1, A2, B1… in the editor and the workout. Stored as `superset_with_next` on plan_exercises and session_exercises (synced like the rest). During the workout, finishing a set of an exercise in a superset goes straight to the next one of the round that still has sets, with no rest; after the last one the rest starts (that exercise's rest time) and the workout goes back to the first one that still has sets. Exercises with no sets left are skipped; anything can still be done in any order by hand. Linking on the fly during a workout is not offered. The workout shows a superset whole: its exercises one under the other, each in its own frame, the one whose set comes next selected (2px border) and marked Next set here; the big button says which (Done set 2 · A2) and follows the round; previous / next move past the whole superset. The AI coach and MCP read and write it too: `superset_with_next` in the plan exchange format (get_workout_plans, propose_plans, manual import), never on the last exercise of a day.

54. **Drop sets.** Per plan exercise (weight x reps only): off, after the last set, or after every set, with the target reps of each drop (1 to 4; `plan_exercises.drop_on`, `drop_reps`). In the workout the sets that have drops show them underneath (kg and reps each, the target as the hint and last time's drop as the reference); one tick saves the set with its drops, the rest starts after it. Each drop is a session_sets row with `drop_index` 1, 2… next to its set (0). Suggestions are per drop, from the same drop last time against its own target (reached = one step up, short = about 5% down, else the same), not from the heaviest weight; with no history a drop starts about 20% lighter per drop. Drops count in volume only: actual max, estimated 1RM, completed sets and the strength score use the main sets (local-db views and the SQL views alike). History shows a set with its drops as 80×8 ↘ 60×10. Adding a set moves the drops to the new last set (after the last set) or gives it its own (after every set). The AI coach and MCP read and write it (`drops: {on, reps}` in the plan format).

55. **Drag to reorder.** Lists that can be reordered use one component (`components/ui/reorder`): hold the grip a moment, slide, drop. Day editor exercises have a grip (the Move up / Move down buttons are gone); in the workout the exercise menu has Reorder exercises, a sheet with the same list. Screen readers get move up / move down actions on the grip.

56. **Swap exercise during a workout** (exercise menu → Swap exercise), for that workout only: the plan does not change. Alternatives are the exercises for the same main muscle not already in the workout (`domain/swap.ts`), ranked by: equipment available where the user trains (profile `training_location`: home = dumbbells, bodyweight, bands; bodyweight = bodyweight, bands; gym = all; the others are listed last and marked), the same way of logging, shared secondary muscles; a search finds any exercise by name. With no set done the new exercise takes the place of the old one with the same sets, reps, rest, superset link and drop set; with some sets done they stay with the old exercise and the remaining sets go to the new one, right after it. The new one gets its own PREVIOUS column and suggestion. UNDO puts the workout back as it was.

57. **Admin panel for anyone.** Same look as the app (warm off-white, white cards, Figtree, sentence case, the accent only on the main action, dark when the computer is dark) and plain language. Sections: Overview (key numbers, new accounts per day), People (search; a person page with plan, activity counts, connected AI apps, Give Premium / Move to Free and a temporary password; counts only, never the content of their data), Password requests, Problems (grouped errors in words, technical details folded), AI coach; under Advanced: All data (every table with a plain name and description, grouped; technical tables folded; a row opens whole and, with editing unlocked, can be changed or deleted; people shown by email, as links), Ask the database (ten ready-made questions that only read, and Write SQL with run / try / run and keep as before, with history), Change log (actions in words) and Backup and reset. 64. **End-to-end encryption of the copy on the server.** Owner's choices: one switch for the whole copy (not per category); the key comes from a passphrase separate from the login password, plus a recovery key; the web app works by entering the passphrase in the browser; the API, MCP and AI apps do not work while it is on (said in the switch's sheet, on the API & MCP page and in every server answer). **Crypto** (`src/lib/vault-crypto.ts`, audited pure JS: `@noble/ciphers` and `@noble/hashes`, already in the lock file as dev dependencies of the Supabase CLI, now app dependencies; randomness from `expo-crypto`; no native package, no change to `.gitignore` / `app.json` / `app.config.js`: the expo fingerprint is the same before and after): a random 256-bit data key per account; each item sealed with **XChaCha20-Poly1305** (random 192-bit nonce per item, safe with random nonces; format = version byte, nonce, ciphertext + tag, base64), with associated data naming the item (`row:<table>:<id>`, `file:<bucket>/<path>`) so the server cannot swap two items. A row is sealed whole (its JSON, `updated_at` included); in clear stay only the table, the row id, the time of the change and the deletion flag (the sync routes and resolves conflicts with them: last change wins per row as before). The data key is wrapped twice: with **scrypt**(passphrase NFKC, 16-byte salt) and with HKDF-SHA256(recovery key) (160 random bits, shown once as 32 Crockford base32 characters in 8 groups; typed back case-insensitively, I/L/O read as 1/1/0); a `key_check` (a known text sealed with the data key) tells a right key from a wrong one. scrypt parameters: Hermes has no JIT, so instead of a fixed N the device that sets the key up measures a 2^12 run and takes the largest N in {2^16, 2^15} that fits in about 1.5 s, at least 2^14 (16 MB; r = 8, p = 1); stored with the salt (`kdf`), so every device derives the same key (a slower one once takes longer); a new passphrase re-measures. Passphrase: at least 10 characters, asked twice. **On the device** the unlocked key is kept in the secure storage the sign-in and the own AI key use (`authStorage`: Keychain / Keystore); the web app keeps it in `sessionStorage` (the tab only: closing it asks again). **Server** (`20261017140000_vault.sql`): `account_sync.encrypted`; `vault_keys` (one row, own only; written by `save_vault_keys`, read by `my_vault_keys`; a trigger refuses replacing the key while encrypted, only the passphrase wrap may change, and a key replaced before turning on drops the items sealed with the old one); `vault_rows (user_id, tbl, row_id, updated_at, deleted, ciphertext ≤ 1 MB, server_at)` with `vault_push` (≤ 500 items, newest change wins, a deletion keeps nothing of the row) / `vault_pull(since)` / `vault_counts`; sealed photos in a new private bucket `vault-files` at `<uid>/p-<hidden name>` (progress photos) or `<uid>/t-<…>` (exercise pictures), the name an HKDF of the data key and the file path. Row level security: own rows only; sealed writes need the copy on, a key set up and the item's category kept (DECISIONS 63, also by the file prefix); `is_premium()` is now false while encrypted, so the readable tables and buckets refuse the account's writes. **Turning it on** (Privacy & data, phones; a sheet: what it means, as one list = the single confirmation: API/MCP stop, nobody at FFT can see the data, if passphrase AND recovery key are lost the server copy is unreadable but the phone keeps its data, other devices ask once; then the passphrase twice; then the recovery key with Copy and an "I saved it" checkbox before the final button): what other devices sent is pulled first, the sync is held, every row goes up sealed (photos too), then `set_vault(true)` flips and deletes the readable copy in the same transaction (`clear_my_online_data`, profile and settings left empty with 1970 times as in DECISIONS 62); the readable files are removed through the storage API (the same retry-at-start list). If anything fails before the flip, the readable copy is untouched and everything is queued to go up readable again. **Off** (confirmed): the sealed copy is pulled, `set_vault(false)` allows readable writes again, everything is queued readable, and once the outbox is empty `clear_vault()` deletes the sealed rows and the key and the app removes `vault-files` (retried at each sync until done). **Other devices** learn it from `my_sync_state()` (now with `encrypted`): they switch mode and queue everything again in the new form (changes the server refused during the switch are not lost), and without the key the plan gate shows the passphrase screen (recovery key one tap away; on a phone "Not now" lets the app run on its own data with the sync waiting; the web app has nothing to show without it). Turning the whole copy off (`set_sync(false)`) also deletes the sealed copy and the key; a category turned off also deletes its sealed rows and files. **Check sync** counts sealed rows (`vault_counts`). **API / MCP / AI apps**: `vault_on_of(user)`; 403 with a clear message (REST and MCP), `create_api_token` refuses (55000), the OAuth page says why. **Admin panel**: the person page shows "End-to-end encrypted" with the number of sealed items instead of the activity counts, and what the copy holds; the table browser lists `vault_keys` and `vault_rows` (unreadable content). **Backups** then hold only ciphertext for these accounts (privacy pages say so). Not done: a new recovery key without turning encryption off and on again; the AI coach (it runs on the device and is unaffected).

73. **Sign in with FFT only for known AI apps; connections that end; Read only first** (`server/oauth.js`, migration `20261018100000_oauth_connections.sql`). **Which apps**: dynamic registration accepts redirect addresses only on an allowlist of exact hosts, https on the default port (`claude.ai`, `claude.com`, `chatgpt.com`, `chat.openai.com`), or loopback (`localhost`, `127.0.0.1`, `[::1]`, any port, http or https: desktop apps and Claude Code receive the code on the user's own computer, so it never leaves it). Anything else (other hosts, look-alikes such as `claude.ai.evil.com`, a port, http, user info, a fragment, custom schemes) is **refused**, not shown with an "unverified" warning: the only use of this sign-in is connecting Claude or ChatGPT, and a warning on a page that looks like ours would still let a phishing app collect a working connection from a hurried user. The check runs again at sign-in, so an app registered before the list gets no code. The owner can approve more hosts after checking them with the server variable `OAUTH_REDIRECT_HOSTS` (comma separated; not set today). Registration is limited to 10 per address per hour and 200 per hour overall (in memory per address, counted in the database overall); an app that registered but never got a connection is forgotten after 30 days (daily clean-up, which also deletes sign-in codes a day after they expire). **The sign-in page** names the host the access goes to, in its own box under the app's name ("If you allow, access to your data goes to **claude.ai**"; for loopback "a program on this computer (127.0.0.1:5173)"), since the app's name is its own claim and the host is not; its CSP allows the form to answer only with a redirect to that app's origin. **Read only is preselected** and listed first (replaces 59's Read and write default); the app's `scope` no longer preselects anything, and a sign-in without a choice (an older page) is read only. **Connections end**: the access token still lasts 7 days; the refresh token now stops after 30 days without use and every connection ends 90 days after the sign-in (`ends_at`; neither token outlives it: sign in again from the AI app); each renewal gives a new refresh token and remembers the replaced one (`prev_refresh_hash`): if a replaced one is used again, someone kept a copy, and the whole connection is ended (OAuth 2.1 refresh token rotation with reuse detection). **Nobody is disconnected by the deploy**: live connections made before count their 30 and 90 days from the migration, and a connection without dates (made by the previous server while the deploy runs) is dated at its next renewal. Already registered apps on approved hosts keep working; an app registered earlier with another host keeps its live connections until they expire, but gets no new sign-in. **In the app**: API & MCP lists connected AI apps apart from personal tokens, each with where its sign-in went (`api_tokens.redirect_host`, written by the server, readable by the owner like the rest of the row; "an app on a computer" for loopback), its permission, when it connected and when it was last used, with Disconnect (Undo, as for tokens). A connection made in the last 7 days is pointed out at the top of the page ("New connection to your data … If it was not you, disconnect it below and change your password").

74. **Admin panel: every look is logged, content hidden by default, no dump download** (`admin/server.js`, `admin/privacy.js`; replaces part of 57). **Logged reads**: every GET of the panel's API writes an `admin_audit` row `read.<page>` with its parameters and the client address (the same page with the same parameters in the same session is logged once per 10 minutes: the badges refresh every minute); if the log cannot be written, the request fails. The Change log page has two lists: Changes (as before) and Views (`read.*`, `row.reveal`). **Hidden by default** in All data: secrets in any schema (columns named like password, token, secret, `*_hash`, otp, nonce, code challenge: `auth.users.encrypted_password`, the tokens' hashes…) and, in public tables that hold a person's own data (every table with `user_id` that is not about the account itself, plus `profiles`; own foods and exercises, the catalogue rows staying readable), every column except keys, owners and times. Hidden values come back as null with a `masked` list per row; the search never looks into them and they cannot be sorted on (both would leak them one guess at a time). **Reveal** (`POST /api/row/reveal`, one row by its key) needs editing unlocked and logs which columns were shown; opening a row with editing unlocked reveals it (editing needs the real values). A new table with `user_id` is hidden unless added to the account tables list (a verify test checks the health, diet and training tables). **SQL needs editing unlocked**, also to read (the ready-made questions too: SQL can read anything, including what the browser hides), and every run is logged (`read.sql` tried, `sql` kept). **No dump download**: `GET /api/backup` (a plain pg_dump of public, auth and storage) is removed with `pg_dump` from the admin image; the copies are the nightly encrypted backups (60), restored as in docs/DEPLOY.md. Counts and account pages (Overview, People, a person) are unchanged and logged like any read.

75. **No database or storage key in GitHub: the APK is published by the api service** (`server/apk.js`, `.github/workflows/publish-apk.yml`). The `Publish APK` workflow had the service-role key (full access to every table and file) in a cron job that ran `npm ci`: any compromised dependency or action could take it. Now the workflow only finds the newest EAS build and calls `POST /internal/apk` on the api service with the build id, its EAS artifact address and the version, authenticated by its own random token `APK_UPLOAD_TOKEN` (GitHub secret); the service keeps only its SHA-256 (`APK_UPLOAD_TOKEN_SHA256`, compared in constant time) and answers 404 while the variable is not set. The service fetches the APK itself, only from `https://expo.dev/artifacts/eas/<id>.apk` (never an address the caller picks freely), checks it starts like an APK (zip), is at most 300 MB, and uploads it and `config.js` to `downloads` with the key it already has; a build already on the page is skipped. Chosen over a storage key limited to the bucket (the self-hosted storage has no per-bucket keys; Railway bucket credentials would mean moving the downloads) and over a signed upload URL (needs a second service to sign). A leaked upload token can only republish one of our own EAS builds. The workflow no longer runs `npm ci`; both workflows pin their actions to commit SHAs and `eas-cli` to an exact version (25.1.1), updated by hand. The manual script (`supabase/scripts/publish-apk.mjs`, service role from `.secrets/`) stays for the owner's computer. Setup and rotation: docs/DEPLOY.md, docs/BREACH.md.

76. **Limits that a caller cannot dodge** (`server/oauth.js`, `server/api.js`, `server/index.js`). **Address**: the api service now takes the caller's address from the LAST `X-Forwarded-For` value (the one Railway's proxy appends), like the admin panel; the first values are whatever the caller sent, so the per-address limit of the AI app sign-in (10 tries a minute) could be dodged with a new fake address for each try. **Per account**: that sign-in checks the password through the auth service from inside Railway, so the auth service's own limits per address only see our server; it now also counts wrong passwords per email (lower case): 5 within 15 minutes lock that email on this page for 15 minutes, whatever the address, with the same message whether the account exists or not, and a locked email is not even checked. The app's own sign-in is not affected (a stranger can at worst delay an AI app connection by 15 minutes). In memory, per server: a restart forgets them. **MCP batches**: a JSON-RPC batch counts one request per message toward the 120 a minute (it counted once), holds at most 20 messages (400 otherwise) and runs them one after the other.

77. **Security headers on the web app and the site, in every location** (`web/security-headers.conf`, `site/security-headers.conf`). nginx drops the server's `add_header` lines in any location that has its own, so the web app's pages (`location /` adds Cache-Control) were served without X-Frame-Options or nosniff, and nothing set a CSP or HSTS. Each service now has one snippet, copied by its Dockerfile to `/etc/nginx/snippets/` and included at server level and in every location that adds a header (a verify test fails otherwise). Headers (all `always`): Content-Security-Policy with `frame-ancestors 'none'`, X-Frame-Options DENY, nosniff, Referrer-Policy no-referrer, HSTS one year (no preload, no includeSubDomains: the domains are Railway subdomains), Permissions-Policy (camera only for the web app's own pages). **Web CSP** fits the Expo static export: scripts from the site plus the one inline line Expo Router writes (`globalThis.__EXPO_ROUTER_HYDRATE__=true;`, allowed by its SHA-256; if Expo changes it the page renders without hydrating), no eval; styles inline (react-native-web writes them at run time); connections to any https address (our backend and API, and the AI provider a user sets with their own key); images also from https, data: and blob:. **Site CSP**: everything from the site only, inline styles allowed (the install page's `<style>`); its one inline script moved to `site/install.js` (a test fails on inline scripts or handlers). The proxied APK and config.js lose the storage's own CSP / frame headers in favour of ours.

78. **Deleted is deleted: soft deletes become real deletes after 7 days** (`purge_deleted` in `20261018120000_purge_deleted.sql`, `LocalDb.purgeDeleted`, `features/premium/sync.ts`). Deleting in the app (and through the API / MCP / coach) still only sets `deleted_at`: the 5 s Undo needs it, and the deletion reaches the server and the other devices as a normal change. **7 days later** the row goes for good. **On the device**: when the database opens and after each sync, rows deleted more than `PURGE_DAYS` (7) ago are removed with their files (progress photos, own exercise pictures), for every account and without one; while the copy on the server is on, each removal is queued as a deletion with its file, so the server row, its file (or the sealed copy of an end-to-end encrypted one) and the other devices' rows go too. The purge follows the server's foreign keys (`schema.ts` `foreignKeys`): a row still used through a `restrict` key (an own exercise in a past workout, a fixed meal with checks) stays, `cascade` children go with their parent (a deleted workout's sets), `set null` children keep their row. Catalogue rows, profiles, settings and consents (the record of what was agreed) are never purged. **On the server**: the api service runs `purge_deleted(7)` every day (rows deleted through the API, devices that never came back): children before parents, each row in its own savepoint (one still referenced stays, counted as `kept`), the files it lists removed through the storage API (removing them from `storage.objects` alone would leave the bytes); then tombstones and sealed deletions older than 90 days go. **Devices away longer**: a device whose last pull is more than 80 days old downloads everything again and drops its own rows the server no longer has (unless waiting to be sent). **Photos**: Photos has a delete button per check-in (a sheet with one button per pose; Undo 5 s); a photo replaced by a new one of the same pose was already marked deleted, so its file now goes after 7 days too. Also fixed: deleting an account with synced rows wrote tombstones for the account being deleted (refused by their foreign key, which made the deletion fail): `record_tombstone` now skips accounts that no longer exist.

79. **Restoring a backup does not bring deleted accounts back; backups kept 6 months** (`20261018130000_deletion_log.sql`, `backup/`). `public.deleted_accounts` holds the id and time of every deleted account (a trigger on `auth.users`, whatever deleted it; RLS on, no policy), kept 7 months. Monthly dumps are now kept 6 months instead of 12 (`backup/retention.mjs`): a deleted account or deleted data leaves the backups within 6 months; daily dumps stay 30 days. Privacy policy and delete-account page updated.

83. **MCP: honest annotations, third-party text marked as data** (`server/api.js`, `server/coach.js`, `src/domain/off-product.ts`, `supabase/functions/off`, `20261018170000_clean_off_names.sql`). Every tool said `destructiveHint: false`; tools that delete or replace data now say `true` (`remove_food_log`, `delete_food`, `update_food`: its portions replace the old ones, `propose_plans`: a changed plan or diet replaces the current one), so AI apps warn harder before them, even with "always allow" for the others. 84. **Deleting an account leaves nothing, and a test proves it** (`20261018180000_account_deletion_complete.sql`, `supabase/verify/db.test.mjs` → "deleting an account leaves nothing", last in the file). Every table with a key to `auth.users` already cascaded; the triggers on `auth.users` now also reach the tables without one: the account's error reports (`app_errors.user_id`) go, admin log entries naming the account (id or email) keep their action and time with the details replaced by `{"account": "deleted"}`, an AI app registration (`oauth_clients`) used only by this account goes, password requests for its email go (81); `deleted_accounts` keeps the id on purpose (79). **The test** (embedded Postgres, `npm run db:verify`): a new account gets a copy of an existing row of every public table that has a user column (unique keys renewed, files moved to its folder; tables empty by then get an explicit row), plus a serving, a password request, an admin log entry, an error report and an AI app of its own; the auth user is deleted (what Delete account does after removing the files); then no column of any public table may still contain the account id or email (except the deletion log), and a phone that was offline pushing its outbox with the old session creates nothing (the foreign keys refuse it). **Guards**: the test fails when a public table has no user column and is not declared as holding no one's data or reached otherwise, when a user column has no `ON DELETE CASCADE` and is not handled by the trigger, and when a storage bucket holding users' files is missing from `delete-account`'s and `reapply-deletions.mjs`'s lists. Not covered here: the storage files themselves (the embedded database has no storage service; the bucket lists are checked instead) and other phones' local copies (documented on the delete-account page). Also fixed on the way (78): the tombstone trigger made deleting an account with synced rows fail.
